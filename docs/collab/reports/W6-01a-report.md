## Deviations
1. **`top[].title` built from `pattern`, not `finding` (packet text says `finding`).** Verified directly against both reference fixtures and the live scan: `issue.finding` is raw source/matched text (e.g. `'    with urllib.request.urlopen(req, timeout=30) as resp:'`), while `issue.pattern` is the short human-readable label (e.g. `'Dynamic attribute access via getattr()'`) that matches the shape of the plan's own alert-schema example title (`'curl to external host in hook'`). Building `top[].title` from `finding` as literally written would put scanned-skill source code straight into `ScanResult` and, eventually, desktop notifications — a direct violation of the packet's own no-file-body invariant one paragraph earlier. Implemented with `pattern`. This is a blocking ask for the Chief to confirm before any downstream packet (W6-01b) is written against this field.
2. **`ScanResult` has 13 fields, not the 12 the packet's Changes section lists** — added `sandbox: str | None = None`. The Sandbox paragraph requires the runner to "record `sandbox=\"none\"` in the result" but the packet's own field list has nowhere to put it. Added a field rather than inventing an out-of-band return value, since `run_scan` needs to surface `sandbox` alongside `tool`/`version`/etc. through one object.
3. **`tree_hash` implemented as the packet specifies (content-hash, mtime-independent), not as `docs/collab/plans/SKILLSPECTOR-INTEGRATION.md` §4 specifies (metadata hash: sorted `(relpath, size, mtime_ns)` plus a marker file's content hash).** The packet's own required test ("stable across mtime changes, differs when a byte changes") only holds for a content hash — the plan's mtime/size hash would do the *opposite* on both cases. Implemented per the packet text and this packet's tests, since they are unambiguous and self-consistent; the plan document's §4 needs a Chief correction (or an explicit note that scan.py's tree_hash and the scout's future root-identity hash for W6-01b are deliberately two different hashes for two different purposes: this one is a content-addressed report cache key, not a cheap watch-trigger key). Flagging this as a blocking ask — W6-01b's queue key and W6-01c's allowlist key both depend on "the tree hash" meaning one thing.
4. **Test fixtures pull `issues` from the raw `skillspector-self.json` and `suppressed` from `skillspector-self-baselined.json`, not solely from the baselined file as the Chief's packet note said.** Verified directly: `skillspector-self-baselined.json` has `issues: []` (all 57 findings moved into `suppressed` by baseline suppression) — following the note literally would leave the `issues`-array sanitization path (REQ10, and required tests (c)/(h)) permanently untested. `self_scan_safe.json` (from the baselined file's `suppressed`, 4 real entries: `AST7 action.py:321`, `AST7 action.py:327`, `AST4 health.py:70`, `TT3 summarize.py:126`) and `self_scan_risky.json` (from the raw file's `issues`, 5 real entries spanning severities: `TT3/CRITICAL`, two `AS1/HIGH` at 1718 and 1093 bytes — both naturally over the 1 KiB truncation threshold with no padding needed, `AST4/MEDIUM`, `AST7/LOW`) are built with real, unmodified field content, only the top-level `issues`/`suppressed`/`components`/`analysis_completeness` arrays trimmed for file size.
5. **`tree_hash` also skips (path+size only, never opened) any regular file whose name matches an "auth"/"credential" substring**, using the same heuristic as `scout.classify_kind`'s `auth` bucket (not imported, duplicated locally to keep `scan.py` decoupled from `scout.py`). This is not in the packet's own REQ list; it closes a concrete gap the security cross-review found: a malicious skill shipping a real (non-symlink) file literally named `credentials.json` would otherwise have its bytes streamed into sha256 by `tree_hash` and separately read by SkillSpector itself. This addition is narrow (filename heuristic only, same as the existing oversized-file fallback path) and does not change `tree_hash`'s required test behavior.
6. **`build_sandbox_argv` refuses (raises `ValueError`) a `root` whose resolved path contains whitespace or starts with `-`/`+`**, before it is ever placed into a `ReadOnlyPaths=` unit property. `ReadOnlyPaths=`/`ReadWritePaths=`/`InaccessiblePaths=` take a whitespace-separated list of absolute paths with `-`/`+` as the only grammar-significant prefixes (verified against `systemd.exec(5)` on this machine, systemd 261 — not a `:` source:dest separator, which belongs only to `BindPaths=`/`BindReadOnlyPaths=`; an earlier security-review draft cited `:` and that was corrected during this packet's own cross-review). Not in the packet's REQ list; added because a non-shell-injection but still real mis-sandboxing vector (a directory name containing a space or a leading `-`/`+`, which an agent-controlled tree could contain) is squarely inside this packet's own sandbox-argv code.
7. **Exit-code contract for `sentinel-scan` (unspecified by the packet) resolved as:** `0` — the CLI ran to completion and printed a `ScanResult` (even if `ScanResult.ok is False` because the scanner's own JSON was malformed/incomplete — that is scanner-reported data, not a CLI failure); `1` — root is not a directory, the sandbox-argv builder refused the root (deviation 6), or the scanner process itself could not be spawned/timed out; `2` — no scanner binary could be resolved (REQ13's explicit "non-zero exit" case, kept distinct from `1` so callers can tell "not installed" from "ran and failed").
8. **`counts` keys use the source JSON's own uppercase severities** (`CRITICAL`/`HIGH`/`MEDIUM`/`LOW`) rather than lowercasing them to match the plan's alert-schema example — the packet does not pin a casing and re-deriving/lowercasing would be one more place to introduce a bug; downstream (W6-01b) can lowercase at the adapter boundary if the alert schema needs it.
9. **`top`'s tie-break for "which 3 of N issues win"** (unpinned by the packet): sorted by severity rank (`CRITICAL` > `HIGH` > `MEDIUM` > `LOW`), then `confidence` descending, then `(file, line)` ascending for determinism.
10. **Truncation marker and cap** (unpinned by the packet, "a marker" / "1 KiB"): fields are truncated to at most 1024 UTF-8 bytes plus the literal marker string `...[truncated]`. `sanitize_report`/`_sanitize_entry`/`_sanitize_value` recurse into nested dicts/lists within each `issues`/`suppressed` entry, so a renamed or relocated `code_snippet`-shaped field is still caught at any depth (security cross-review's specific ask), not just at the top level of each issue.
11. **Left `daemon.py`'s `OPERATIONAL_NAMES`/self-path logic untouched.** All five analysts independently and mechanically confirmed that writing `state_dir()/scans/<tree_hash>.json` while a live daemon is watching `state_dir()` will raise a genuine `R-SELF` "write to sentinel path by unknown" alert (`OPERATIONAL_NAMES` is a fixed exact-basename allowlist that cannot match a per-hash filename, and `_on_fs_event` never supplies a writer PID, so `_is_sentinel_writer(None, None)` is always `False`). This is real and reproducible today (a live sentinel daemon was confirmed running on this machine during the cross-review), but fixing `daemon.py`'s self-tamper allowlist is outside this packet's own Changes section and touches file(s)/logic that `W3-07` (a different, currently-unmerged packet) also owns — widening `OPERATIONAL_NAMES` to a path-prefix check here risks a merge collision with W3-07's planned StateLedger rewrite of the same mechanism. Flagging this explicitly rather than silently absorbing it or silently fixing someone else's in-flight packet: **this needs a Chief decision on whether W6-01a, W6-01b, or W3-07 owns the fix**, and once W3-07's control-socket protocol lands, every `sentinel-scan` write becomes a guaranteed foreign-write alert unless `sentinel-scan` is taught to announce over that socket too.
12. **`ScanResult`'s field names (`score`/`recommendation`/`report_path`) intentionally do not match `investigate.py`'s already-shipped `_render_new_agent` consumer**, which expects `evidence['scan']` shaped `{tool, version, risk_score, verdict, counts, report, top}` (locked in by `tests/test_investigate.py`'s `risk_score=8.5`/`verdict='review'` fixture). Per the packet's own Non-goals ("triggering scans ... and the panel's risk bar wiring" are W6-01b/W6-01c), building that adapter is out of scope here. Noting it explicitly so W6-01b's author builds `ScanResult` → `evidence['scan']` translation from day one instead of discovering the mismatch late.
